游戏 Wiki 站上站 SOP

这是给人看的中文 HTML 版 SOP，用于按照课程方法从筛词、数据准备、模板换皮、内容生产、SEO、上线、数据诊断、广告和外链一路执行。项目维护源仍然是 docs/GAME_SITE_SOP.md。

适用：静态游戏 Wiki / 攻略站 架构：Next.js 静态导出 + Cloudflare Pages 来源：10 个课程 HTML 用途：上站执行与自检

0. 执行原则

  • 先大量做站，不要在前几个站上过度打磨。
  • 选游戏看搜索需求，不按个人喜好。
  • 新词要快，能当天上就不要拖。前 10 个站之前，速度比自动化更重要。
  • 一页只服务一个关键词和一个搜索意图。
  • 上线后的数据是反馈，不是情绪来源。除非影响索引、用户体验、广告或部署，不要反复大改老站。
  • 母模板只放通用能力；具体游戏的品牌、域名、内容、广告 key 放在子仓库。
  • 生产架构固定为 Cloudflare Pages 静态导出。
核心口径：不是做一个完美站，而是用稳定模板快速验证一批游戏词，然后把真实反馈沉淀回下一站。

1. 筛词与建站判断

输入

  • 候选游戏名。
  • Google Trends 曲线。
  • KD 或同类关键词难度信号。
  • Google 搜索结果：游戏主词、游戏名 wiki。
  • YouTube / TikTok / 社区近期热度。
  • 游戏类型：Roblox 或非 Roblox。

执行

  1. 先看 Google Trends。保留上升或刚开始上升的词，谨慎处理已经明显回落的词。
  2. 看 KD。新站优先 KD 30 以下；30-60 作为中等难度；主词高 KD 时，只做长尾机会明确的页面。
  3. 看 SERP。搜索游戏名和 游戏名 wiki，记录首页独立小站、Fandom、官方 wiki、大媒体和成熟攻略站。
  4. 判断游戏类型。Roblox 游戏通常更适合 codes、tier list、map、boss、progression 等页面；非 Roblox 游戏要确认生命周期和内容深度。
  5. 排除风险词：cheats、hacks、exploits、scripts、pastebin、auto farm、no-key、infinite money 等。

产出

  • 游戏名、目标域名、主关键词。
  • Top 10 长尾关键词。
  • Trends 判断、SERP 竞争判断、Go / No-go。
  • 值得参考的竞品页面。
验收：必须能说明这个游戏为什么可能有搜索流量，以及第一批页面分别满足什么需求。

2. 竞品与复刻目标

执行

  1. 搜索游戏主词，不只搜 游戏名 wiki。
  2. 找低权重但排名靠前的独立小站，这类站证明页面结构和内容本身有效。
  3. 检查它是否有首页、列表页、文章详情页、内链、清晰导航和较高信息密度。
  4. 只选一个主要复刻目标，不要一开始拼多个设计。
  5. 保存首页、列表页、文章页、Header、Sidebar、Footer、移动端和广告位截图。

产出

  • 复刻目标 URL。
  • 首页 URL、列表页 URL、文章页 URL。
  • 要复刻的结构和不要复制的问题。
验收：动手设计前，必须有一个明确目标站。

3. 子仓库设置

  1. 为每个游戏站创建单独子仓库。
  2. 从母模板复制或 fork 到子仓库。
  3. 英文公开 URL 不加 /en。
  4. 设置 NEXT_PUBLIC_SITE_URL 和 CLOUDFLARE_PAGES_PROJECT。
  5. 游戏品牌、域名、关键词、内容、图片、广告 key、统计 key 都放子仓库，不写回母模板。
验收：子仓库能独立运行和构建，不需要改母模板。

4. 建站数据准备

需要收集

基础信息

  • 游戏名、短名、平台、类型。
  • 上线 / 更新状态。
  • 游戏官网、Roblox/Steam 页面。
  • Discord、YouTube、联系邮箱。
  • 域名、主题色、Logo、favicon、Hero 图。

首页模块

  • Codes。
  • Beginner guide。
  • Tier list。
  • Maps、Bosses。
  • Classes / races / factions。
  • Weapons / skills / builds / progression。

内页关键词

  • 主关键词。
  • 长尾关键词。
  • 搜索意图。
  • 建议内容类型。
  • 优先级。
  • 数据来源信号。

产出文件

  • 00-basic-info.md
  • 00-homepage-modules.md
  • 01-keywords.csv 或同等表格
  • 02-content-plan.md
  • 媒体素材来源记录
验收：后续建站可以完全根据这些资料执行，不靠猜游戏事实。

5. 基础换皮

  1. 替换 SITE_CONFIG：游戏名、站点名、短名、Logo 文案、描述、默认标题、联系邮箱、官方链接。
  2. 替换媒体：Hero 图、视频缩略图、YouTube ID、favicon、manifest。
  3. 用现有主题系统替换颜色，不新增一套平行主题。
  4. 替换 About、Contact、Privacy、Terms、Copyright。
  5. 清理旧游戏残留：旧游戏名、旧域名、旧文章 URL、旧官方链接、旧视频、旧图、旧广告 key。
验收：全局搜索旧游戏和旧域名，公开输出里不应残留。

6. 首页制作

  1. 首页组件保持通用，不在组件里硬编码游戏文案。
  2. 首页内容放在 locale/config 数据里。
  3. 首页 title 和 description 对准游戏主查询。
  4. 首屏必须清楚显示游戏 / 站点身份。
  5. 有真实 gameplay / trailer 视频时，把视频模块放在 Hero 附近。
  6. 用真实需求组织首页模块：最近更新、新手指南、热门攻略、游戏介绍、功能模块、FAQ、最终 CTA。
  7. 首页模块只链接已存在的导出路由；没有文章时显示真实空状态或只做信息展示。
  8. 上线前删除占位 stats、占位 codes、假官方链接和模板文案。
验收：首页只有一个 H1，有强游戏识别、有效链接、无断链、无旧游戏文案。

7. 文章与内容生产

  1. 文章放在 content/en/<content-type>/<slug>.mdx。
  2. 使用 JavaScript metadata export，不用 YAML frontmatter。
  3. 必填 metadata：title、description、category、date。
  4. 可选 metadata：image、summary、lastModified、badge。
  5. MDX 正文从 H2 开始，不在文章里写 H1。
  6. 一篇文章只解决一个搜索意图。
  7. 正文顶部要先给直接答案。
  8. 需要比较时用表格；需要操作时用步骤；常见问题多时加 FAQ。
  9. 加相关内链；外链只放真实有用来源。
  10. 英文内容和路由稳定后再做翻译。
  11. 删除旧示例内容，或确保旧内容不导出。
验收：每篇文章意图明确、metadata 完整、渲染后只有一个 H1，并有有用内链。

8. 导航、内链与 URL

  1. 英文 URL 不加 /en。
  2. 导航来自实际内容分类，不照搬旧游戏结构。
  3. 导航标签短、清楚、可扫读。
  4. 保证每个公开页面能通过 Header/Footer、Sidebar、首页模块、文章内链、XML sitemap、HTML sitemap 被发现。
  5. 不要链接不存在的页面。
  6. 检查旧页面不要进 sitemap。
  7. 列表页要有分类标题、描述、文章卡片；无内容时有空状态。
验收：内部链接检查通过，公开 URL 不出现 /en。

9. SEO 工程化

  1. NEXT_PUBLIC_SITE_URL 必须存在。
  2. canonical、sitemap、robots、OG、Twitter、JSON-LD 都用生产域名。
  3. 按页面类型设置 metadata：首页对主词，列表页对分类词，文章页对文章关键词。
  4. 结构化数据：Homepage 用 WebSite、Organization、FAQ；列表页用 ItemList；文章页用 Article、BreadcrumbList、FAQ。
  5. 图片 alt 写真实游戏/媒体内容。
  6. robots.txt 允许抓取并声明 sitemap URL。
  7. sitemap 从真实路由和 MDX 内容生成。
  8. 提供 HTML sitemap，并在 Footer 链接。
验收：导出的页面包含正确 metadata 和结构化数据，且域名是子站域名。

10. 本地验证

部署前必须跑：

npm ci --legacy-peer-deps
npx tsc --noEmit
NEXT_PUBLIC_SITE_URL=https://example.wiki npm run build
npm run preview:static
npm run check:urls
npm run check:internal-links

把 https://example.wiki 换成真实生产域名。

还要人工/浏览器确认

  • /、/contact、/sitemap、/robots.txt、/sitemap.xml 返回 200。
  • 配置广告时，/ads.txt 返回 200。
  • /en 不公开导出。
  • 旧游戏 URL 不存在或返回 404。
  • 桌面和移动端无横向滚动、遮挡、重叠、隐藏 CTA。
  • 浏览器 console 无相关运行时错误。
未通过 typecheck、静态构建、sitemap、内部链接、浏览器检查之前，不要部署。

11. Cloudflare Pages 上线

  1. 使用 Cloudflare Pages 静态导出部署。
  2. 设置生产环境变量：NEXT_PUBLIC_SITE_URL、需要时的 analytics 变量、ad 变量。
  3. 从子仓库部署。
  4. 上线后验证：首页、代表性列表页、代表性文章页、联系/法律页、sitemap、robots、ads.txt。
  5. 确认生产源码/导出内容里没有旧游戏和旧域名残留。
验收：生产页面正常渲染，sitemap 和内部链接检查通过，才算上线完成。

12. GSC / GA / Clarity 与索引

  1. 把生产域名添加到 Google Search Console。
  2. 优先用 DNS 验证所有权。
  3. 提交 /sitemap.xml。
  4. 需要统计时安装 GA4。
  5. 需要行为诊断时安装 Microsoft Clarity。
  6. 确认统计脚本只在环境变量存在时出现。
  7. 至少等两天再判断流量。

诊断顺序

  1. Google 能否访问站点？
  2. sitemap 是否提交并接受？
  3. 页面是否被发现？
  4. 页面是否被索引？
  5. 是否有 impressions？
  6. 排名是否接近可点击位置？
  7. 用户是否因为页面不满足意图而跳出？
验收：GSC 正确显示站点和 sitemap；GA/Clarity 要么验证已接入，要么明确未启用。

13. 广告变现

  1. 广告 key 不放母模板，只放子站环境变量。
  2. 为子站配置 ads.txt。
  3. AdSense：添加站点、验证域名、通过 env 注入 Publisher ID，只在 ID 存在时渲染脚本。
  4. Adsterra：子站单独添加网站、单独创建广告单元、banner/sidebar/sticky 使用独立 env。
  5. 隔离 banner 脚本，避免多个广告位共用 window.atOptions 互相覆盖。
  6. 不要给攻略站启用 Popunder、Social Bar、Smartlink 或强跳转广告。
  7. 桌面和移动端都要检查：无弹窗、无自动跳转、无遮挡、无横向溢出，首屏仍以有用内容为主。
验收：广告只在配置后渲染，且不破坏用户体验。

14. 上线后诊断

  1. 不要太早诊断。部署并提交 sitemap 后至少等两天。
  2. 手动 Google 搜：游戏名、游戏名 wiki、核心长尾页。
  3. 看 Trends：需求下滑可能是词的问题；需求上涨但无 impressions，优先查索引和内链。
  4. 看 GSC：sitemap、索引页、impressions、平均排名、CTR、抓取错误。
  5. 看 GA4：sessions、engagement、source/medium、top pages。
  6. 看 Clarity：rage clicks、dead clicks、scroll depth、移动端可用性问题。
  7. 如果只有首页出现：加强首页到内页链接，确认 sitemap 包含内页，Footer 放 HTML sitemap，加文章互链。
  8. 如果有索引没点击：改 title/description，首屏答案更直接，对比 SERP 竞品。
  9. 如果排名下降：先确认游戏趋势、竞品变化、近期站点改动，不要无证据重写全站。

诊断产出

  • 已确认事实。
  • 最可能原因。
  • 唯一下一步动作。
  • 暂时不改什么。
验收：每个结论都要对应 GSC、SERP、Trends、GA、Clarity 或生产行为证据。

15. 外链

  1. 站点还没证明索引或流量潜力前，不急着发外链。
  2. 用竞品外链研究找平台类型。
  3. 优先相关场景：社区帖、网站目录、profile、文章投稿、论坛或问答中自然补充链接。
  4. 避免假高权重、垃圾评论、无关留言和平台滥用。
  5. 外链是运营动作，不是母模板代码。

记录字段

  • Source URL、Target URL、Anchor text、rel 类型、状态、日期。
验收：外链相关、可追踪，不要求修改母模板。

16. 复盘迭代

  1. 每个站记录：关键词、域名、上线日期、构建/部署结果、索引状态、早期 impressions/clicks、排名截图、错误、下次复用点。
  2. 不要无证据反复重写已上线站。
  3. 模板级问题修母模板。
  4. 子站内容问题只修子站。
  5. 如果是关键词需求问题，记下经验，继续做下一个游戏。
验收：下一个站至少带着上一个站的一条明确改进开始。

17. Codex 执行口径

  1. 用户提供目标游戏名和域名。
  2. Codex 先读 COURSE_SOURCE_FILES.md、GAME_SITE_COURSE.md、GAME_SITE_SOP.md、GAME_SITE_LAUNCH_CHECKLIST.md 和相关子仓库文件。
  3. Codex 创建或更新子站 requirements pack。
  4. 默认只改子仓库；确认为母模板级问题时才改母模板。
  5. 验证：typecheck、静态导出 build、sitemap check、internal link check、桌面/移动端浏览器检查。
  6. 汇报：changed files、dependency changes、verification commands、失败检查、风险边界、commit/push 状态。

18. 停止条件

  • 必要源文件缺失。
  • 域名或生产目标未知。
  • 需要外部平台登录、付款、权限、验证码或账号设置。
  • 破坏性文件操作会影响当前项目外文件。
  • 构建或验证失败，且失败点超出当前请求范围。
  • SOP 与 AGENTS.md 冲突；此时 AGENTS.md 优先。
停止不是放弃，而是避免在权限、生产环境、外部平台和高风险文件操作上误伤。
